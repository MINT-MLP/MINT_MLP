# 07. 추천 알고리즘 재설계

> **2026-09-17 전제 변경: 크롤 DB는 쓰지 않기로 확정.** 이 문서의 2절(크롤 DB로 메워지는 것)·3절(목표 구조)·6절(무드 태깅)은 크롤 DB를 전제로 쓰였으므로 그대로 적용할 수 없다. 4절의 스코어링 골격(하드 필터 / 매칭 축 / 품질 보너스 분리, 가중 거리, 점수 비례 샘플링)과 5절 랜덤성, 9절 로그 설계는 데이터 출처와 무관하게 유효하다. 알고리즘은 현재 데이터 출처(네이버 검색 + 공공데이터 + 버즈 캐시) 안에서 다시 설계해야 한다.


논의일: 2026-09-15
상태: 설계 합의 완료, 구현 미착수
전제: 네이버 플레이스 크롤링으로 서울·경기 장소 데이터 축적 중

## 결론 요약

- 현재 추천은 **네이버 검색으로 후보를 긁고 LLM이 이름만 보고 찍는 구조**다. 사용자 선택 항목 대부분이 검색어에 들어가지 않는다.
- 크롤 DB로 옮기면 **조건 6종이 추측에서 실제 필드로** 바뀐다. 이게 정확도 개선의 대부분이다.
- LLM은 제거가 아니라 **런타임에서 배치 태깅으로 이동**한다.
- 랭킹은 **가중치 스코어**로 간다. 임베딩이 아니다. 2축이면 v1으로 충분하다.
- 태깅해야 하는 건 **무드 축 하나**뿐이다. 가격은 메뉴에서 계산되고 조건은 amenities에 이미 있다.

## 1. 현재 구조의 한계

### 선택 항목이 실제로 가는 곳

| 항목 | 네이버 검색어 | 후보 필터 | 프롬프트 텍스트만 |
|---|---|---|---|
| 목적 밥/술/카페/기타 | 키워드 풀 10개 선택 | | |
| 장르 9종 | 키워드 풀 교체 | | |
| 직접 입력 메뉴 | 그 메뉴가 검색어 | | |
| 지역 | 검색어 접두사 | 주소 토큰·반경 | |
| 인원 5명 이상 | "단체 " 접두사 | | 단체석 문구 |
| 예산 | "가성비 "/"고급 " 접두사 | | 1인 예산 문구 |
| 관계 | 추가 키워드 2개 | | 문구 |
| 특별한 날 | 추가 키워드 3~4개 | | 힌트 문구 |
| 편식 | | 이름·카테고리 토큰 제거 | 절대 제외 문구 |
| **분위기 14종** | | | **텍스트 한 줄** |
| **조건 6종** | 상위 3개만 | | **필수 키워드 문구** |
| 재추천 가중치 | | | 텍스트 |

관련 코드: 검색어 조립 [recommend.ts:455-545](../api/recommend.ts#L455-L545), 프롬프트 조립 [recommend.ts:1062-1236](../api/recommend.ts#L1062-L1236)

### 왜 이 방식으로는 안 되나

1. **조건은 검증할 소스가 없다.** 주차·룸·예약·늦게까지·반려동물·역세권은 사실 여부가 있는 항목인데, 파이프라인 어디에도 그 사실을 아는 데이터가 없다. 모델이 가게 이름과 카테고리 문자열만 보고 추측한다.
2. **분위기는 네이버 단계에 아예 없다.** 조용하게를 골라도 후보는 "홍대 맛집, 홍대 한식, 홍대 고깃집"으로 뽑힌다.
3. **조건 4개 이상이면 잘린다.** 조건 6종과 추천 태그 8개를 합쳐 상위 3개만 검색어로 간다.
4. **쿼리당 5건 상한.** 네이버 지역검색 `display=5`가 최대. 후보 풀이 50~70개뿐이라 조건이 겹칠수록 교집합이 후보 밖으로 밀린다.
5. **LLM이 보는 정보가 빈약하다.** `formatNaverPlaces`가 넘기는 건 `이름 | 카테고리 | 주소 | 좌표` 네 개뿐이다. 평점·리뷰·가격·영업시간·좌석이 없다.
6. **재현이 안 된다.** 같은 입력에 매번 다른 결과가 나와서 가중치를 튜닝해도 좋아졌는지 확인할 방법이 없다.

결과 카드에 "조용한 분위기"라고 뜨는 건 모델이 생성한 `vibeTags`이지 검증된 속성이 아니다. UI는 조건 필터처럼 보이는데 실제로는 검색 엔진 위의 추측이고, 그 간극이 신뢰 문제로 이어진다.

## 2. 크롤 DB로 메워지는 것

### 조건 6종: 0/6 → 6/6

| 조건 | 현재 | 크롤 DB |
|---|---|---|
| 주차 가능 | LLM 추측 | amenities |
| 룸 있는 곳 | LLM 추측 | amenities 단체석·룸 |
| 예약 가능 | LLM 추측 | amenities |
| 늦게까지 | LLM 추측 | hours |
| 반려동물 | LLM 추측 | amenities |
| 역세권 | LLM 추측 | PostGIS + 지하철역 좌표 |

### 부수 효과

- **예산이 진짜 필터가 된다.** 메뉴 테이블에 `price`가 있다. 현재 `priceRange`는 모델 환각이다.
- **후보 풀이 50여 개에서 수십만 행으로.** 조건이 겹쳐도 교집합이 남는다.
- **거품 지표가 공짜로 생긴다.** `visitor_review_count` 대 `blog_review_count` 비율이 곧 협찬 신호다. 지금 [blogBuzz.ts](../api/_lib/blogBuzz.ts)가 네이버 블로그 검색 크론으로 18개 지역만 워밍하며 어렵게 추정하던 것을, 전 지역에서 추가 호출 없이 얻는다.
- **재현성.** 같은 입력에 같은 결과. 튜닝과 테스트가 가능해진다.

### 조건부

**무드는 태깅 품질에 전적으로 달렸다.** 다만 현재 기준선이 "모델이 가게 이름만 보고 찍기"라 바닥은 낮다.

### 오히려 나빠질 수 있는 것

- **폐업.** 실시간 네이버 검색은 최소한 지금 존재하는 곳만 돌려준다. DB는 죽은 가게를 추천할 수 있다. 조건이 좀 안 맞는 것보다 훨씬 크게 신뢰를 깬다. **재방문 주기와 폐업 감지가 정확도 튜닝보다 먼저다.**
- **커버리지.** 서울·경기 밖은 결과가 없다. 지금은 전국이 동작하므로 커버 밖은 기존 경로로 폴백하는 이중 구조가 필요하다.

## 3. 목표 구조

```
[빌드타임]
크롤 → 키워드리뷰·본문·메뉴·amenities 파싱
     → 무드 축 태깅 (곳당 숫자 1개 + confidence)
     → 가격대 계산 (메뉴 중앙값)
     → DB 컬럼에 저장

[런타임]
하드 필터 (WHERE)  → 후보 수백 개
가중치 스코어 정렬 → 상위 K
샘플링            → 최종 6곳
```

런타임 LLM 호출은 없앤다. 나중에 맥락 설명이 필요해지면 최종 6곳만 넘기는 얇은 호출을 추가할 수 있다.

## 4. 스코어링 설계

### 항목을 세 종류로 나눈다

이게 설계에서 가장 중요하다. 성격이 다른 걸 한 축에 넣으면 반드시 깨진다.

| 종류 | 예 | 처리 |
|---|---|---|
| **하드 제약** | 편식, 주차, 영업 중, 장르, 지역 | WHERE 절. 거리로 환산 금지 |
| **매칭형** | 가격, 무드 | 원하는 값이 있고 멀어지면 감점. 양방향 |
| **품질형** | 신뢰도, 리뷰 건전성, 청결 | 사용자가 고르지 않음. 항상 높을수록 좋음. 가산점 |

### 왜 스칼라 합산은 안 되나

| 사용자 | 선택 | 합산 |
|---|---|---|
| A | 조용하게 3 + 주차 2 + 저예산 1 | 6 |
| B | 시끌벅적 1 + 룸 2 + 플렉스 3 | 6 |

정반대 취향인데 같은 6점이고 같은 가게를 추천받는다. 배점을 조정해도 여러 값을 한 숫자로 뭉개는 이상 안 없어진다. 그리고 스칼라에는 방향이 없어서, 8점 가게가 6점 사용자에게 뭐가 과한 건지 말할 수 없다.

### v1 축 구성

검토했던 4차원 (장소, 가격, 무드, 기타)의 판정:

| 항목 | 판정 | 이유 |
|---|---|---|
| 장소 | 축 아님 | 좌표라 점수 환산 불가. 강남 3점, 홍대 5점이 성립 안 함. PostGIS WHERE |
| 가격 | 축 맞음 | 메뉴 중앙값 |
| 무드 | 조건부 | 하나의 스펙트럼으로 정의해야 함 |
| 기타 | 해체 | 하드·매칭·품질이 섞여 있음 |

**결과: 매칭 축 2개 (가격, 무드) + 하드 필터 + 품질 가산점.**

### 공식

```
후보 = WHERE(지역 반경, 목적 카테고리, 편식 제외,
            예산 상한, 영업시간, 조건 6종)

점수 = 품질점수
     − w_price × |사용자예산  − 장소가격|
     − w_mood  × |사용자무드  − 장소무드|
     + 태그보너스

최종 = 상위 K에서 점수 비례 샘플링
```

### 설계 주의사항

- **안 고른 축은 가중치 0으로 빼라.** 0점으로 채우면 고르지도 않은 차원이 조용히 결과를 왜곡한다. 가장 흔한 버그.
- **무드 축은 한 가지 뜻만 담아라.** "조용함 0 ~ 시끌벅적 1" 같은 단일 스펙트럼. 감성적인과 조용한을 같은 축 점수로 섞으면 위의 A/B 반례가 무드 축 안에서 재발한다.
- **중앙 쏠림을 만나게 된다.** 모든 축에서 중간값인 무난한 집이 누구에게나 가까워 상위권에 붙는다. 고른 축의 가중치를 비선형으로 키우거나 임계 미달에 페널티.
- **축 밖 분위기 라벨은 태그 가산점으로.** UI에 14개가 있는데 축은 하나뿐이라 감성적인·힙한 등이 갈 곳이 없다. 태그 배열로 남기고 매칭 시 소폭 가산점만. 거리 계산에는 넣지 않는다. UI를 줄일 필요도 없고 구현도 몇 줄이다.

### 기존 코드와의 접점

[scoring.ts](../api/_lib/scoring.ts)의 `computeFinalScores`가 이미 바깥 레이어다. 버즈 감점과 발굴 가산을 하고 있으니, 입력으로 받던 `fitScore` 자리에 위 공식을 넣으면 골격이 완성된다.

그리고 **점수 명세서는 이미 쓰여 있다.** 현재 프롬프트의 fitScore 100점 배분표가 그대로 설계도다. 전임자가 배점을 다 정해놓고 해석만 LLM에 맡긴 상태다.

| 항목 | 배점 | 계산 근거 |
|---|---|---|
| 분위기 일치 | 35 | 무드 축 거리 + 태그 보너스 |
| 목적 적합 | 20 | 카테고리 매핑 테이블 |
| 예산 적합 | 15 | 메뉴 중앙값과의 거리 |
| 시간 적합 | 10 | hours 파싱 + 혼잡도 |
| 신뢰도 | 20 | 방문 대 블로그 리뷰 비율, 리뷰 절대량, 업력 |

### 정체성

이건 **가중치 스코어**이고 검색 랭킹 용어로는 feature-based ranking이다. 자료를 찾을 때 키워드는 "콘텐츠 기반 필터링", "weighted scoring model"이다.

**임베딩 맵이 아니다.** 지금 단계에서 임베딩으로 가면 안 되는 이유:

| | 이 설계 | 임베딩 맵 |
|---|---|---|
| 차원 | 2개 | 수백~수천 |
| 축의 의미 | 사람이 정함, 해석 가능 | 학습 결과, 해석 불가 |
| 조회 | SQL 산술식 정렬 | ANN 인덱스 유사도 |
| 튜닝 | 가중치 수동 조정 | 재학습 |

1. **하드 필터와 궁합이 나쁘다.** 주차 있는 곳만 같은 제약은 벡터 유사도로 표현이 안 된다. pgvector에서 메타데이터 필터와 ANN을 섞으면 pre/post-filtering 문제가 생긴다. 이 서비스는 필터가 주인공이다.
2. **반의어 문제가 정확히 무드 축을 때린다.** 텍스트 임베딩은 "조용한 분위기"와 "시끄러운 분위기"를 가깝게 본다. 문맥이 거의 같아서다. 가장 중요한 축에서 정반대를 구분 못 한다.
3. **해석 불가능성이 튜닝을 막는다.** 현재 문제가 "왜 이 집이 나왔는지 모르겠다"인데 임베딩은 악화시킨다.

임베딩이 맞는 자리는 따로 있다. **"이 집이랑 비슷한 곳 찾기"**는 장소에서 출발하는 탐색이라 필터 문제도 해석 부담도 없다. 발굴 탭을 제대로 만들 때 쓴다.

## 5. 랜덤성

목적이 세 개인데 섞으면 전부 망가진다.

| 목적 | 올바른 해법 |
|---|---|
| 재추천 다양성 | 랜덤 아님. 제외 목록 + 다음 순위. `excludeNames`가 이미 그 역할 |
| 노출 공평성 | 점수 비례 가중 샘플링. 진짜 랜덤이 필요한 자리 |
| 탐색 | 학습 데이터 편향 방지용. 나중 단계 |

**구현 원칙**

- 상위 K 안에서만 뽑는다. 전체에서 뽑으면 품질이 무너진다.
- 온도 파라미터 하나로 강도 조절. 0이면 결정론, 높이면 균등에 가까워진다.
- **시드는 세션키로 고정.** 새로고침마다 결과가 바뀌면 "아까 그 집 어디 갔지"가 된다. 세션 안에서는 재현되고 세션이 바뀌면 달라져야 한다.
- **끌 수 있게 플래그를 둔다.** 랜덤은 측정 가능성을 해친다. 가중치 튜닝과 평가에서는 꺼야 한다.

## 6. 무드 태깅 방법

가장 어려워 보이지만 실제로는 풀려 있다. **본인이 판정할 필요가 없다. 리뷰어들이 이미 했다.**

### 난이도 순서

- **1순위. 키워드리뷰 카운트 비율.** 네이버 플레이스의 "이런 점이 좋았어요" 선택형 태그와 카운트. 정온도에는 "대화하기 좋아요"가 거의 그대로 매핑된다. 시끄러운 데서는 대화가 안 되니까. SQL만으로 끝나고 LLM도 본문 분석도 필요 없다. 대부분 여기서 해결된다.
- **2순위. 본문 정규식.** 시끄러·조용·떠들·웨이팅 같은 단어 빈도. 1순위로 애매한 것만.
- **3순위. LLM 판정.** 위 둘로도 안 되는 소수만.

20만 곳 전부 LLM 돌릴 일이 아니다.

> **확인 필요**: 크롤러가 리뷰 본문만 긁는지 키워드리뷰 칩까지 긁는지. 안 긁고 있으면 최우선 작업.

### 카테고리 기본값 + 리뷰 보정

0부터 시작하지 말고 카테고리 기본값을 깔고 보정하면 작업량이 줄고 콜드스타트도 해결된다.

| 카테고리 | 정온도 기본값 |
|---|---|
| 북카페, 티카페, 오마카세 | 0.1 |
| 카페, 브런치, 와인바 | 0.35 |
| 한식당, 일식당 | 0.5 |
| 고깃집, 이자카야 | 0.7 |
| 포차, 호프, 술집 | 0.85 |

리뷰 신호로 상하 0.2 정도 움직인다. 리뷰 없는 신규 가게도 값이 생기고 카테고리만으로 이미 절반은 맞는다.

### 절대값이 아니라 순서

이건 분류가 아니라 랭킹이다. 어떤 집이 0.6인지 0.65인지는 아무도 모르고 결과에도 영향이 없다. **조용한 집이 시끄러운 집보다 낮기만 하면 된다.** 완벽한 값을 뽑으려다 막히는 것보다 대충 맞는 순서를 먼저 만드는 게 낫다.

**confidence를 같이 저장한다.** 리뷰 5개짜리의 0.3과 800개짜리의 0.3은 다르다. 낮으면 점수에서 깎거나 상위 노출에서 뺀다.

### 가보지 않아도 되는 검증법

- **극단 확인.** 정온도 상위 20곳과 하위 20곳을 이름·카테고리만 본다. 조용한 쪽에 포차가 있으면 틀렸다. 5분이면 된다.
- **분포 확인.** 값이 0.5 근처에만 뭉쳐 있으면 판정이 작동 안 한 것. 히스토그램 한 장.
- **아는 가게 30곳 스팟체크.**
- **2D 산점도.** 축을 둘 이상 만들면 두 개씩 뽑아 산점도. 카페가 한 구석에 뭉쳐 있으면 기준이 무너진 것.

## 7. LLM 비용

### 현재 상태 정정

**이미 Haiku를 쓰고 있다.** [recommend.ts:1247](../api/recommend.ts#L1247) 기본값이 `claude-haiku-4-5-20251001`. 7월에 Sonnet 5로 갔다가 되돌린 이력이 있다. 여기서 더 깎을 게 없다.

**진짜 구멍은 529 폴백.** [recommend.ts:1272](../api/recommend.ts#L1272)가 과부하 시 조용히 Sonnet 4.6으로 올라간다.

| 경로 | 입력 $/MTok | 출력 $/MTok |
|---|---|---|
| 기본 Haiku 4.5 | $1 | $5 |
| 529 폴백 Sonnet 4.6 | $3 | $15 |

3배인데 로그도 알림도 없고, 재시도가 try 블록 바깥이라 두 번째 실패는 500이 된다. Haiku 재시도로 바꾸거나 최소한 계측을 붙인다.

### 제공사 비교

리스트 가격은 OpenAI 소형 모델이 싸다. 2026-09-15 확인.

| 모델 | 입력 $/MTok | 출력 $/MTok |
|---|---|---|
| gpt-4o-mini | $0.15 | $0.60 |
| gpt-5.4-nano | $0.20 | $1.25 |
| Claude Haiku 4.5 | $1.00 | $5.00 |

양쪽 다 Batch API 50% 할인, 캐시 입력 약 10%.

실제 절감액. 태깅은 20만 곳에 배치 할인, 런타임은 표준 단가.

| 항목 | Haiku 4.5 | gpt-4o-mini |
|---|---|---|
| 태깅 20만 곳 1회 | $275 | $39 |
| 런타임 월 1만 건 | $100 | $14 |

가정: 곳당 입력 2,000토큰·출력 150토큰, 런타임 요청당 입력 5,000·출력 1,000.

### 판단

- **구조 변경이 100배, 제공사 교체가 6배.** 순서는 구조가 먼저다. 구조를 바꾸면 런타임 호출이 거의 사라져 단가가 걸리는 자리는 태깅 배치 하나로 좁아진다.
- **옮긴다면 런타임이 아니라 태깅부터.** 런타임 프롬프트는 79커밋 튜닝 결과라 재튜닝 비용이 크다. 태깅 프롬프트는 새로 쓰는 것이라 부담이 없다.
- **한국어 리뷰 품질이 실제 변수.** 단가로는 알 수 없다. 20만 곳을 잘못 태깅하면 재태깅이 단가 차이를 넘는다.
- **결정은 데이터로.** 200곳 정답셋을 만들고 후보 모델들을 같은 입력으로 돌려 태그 일치율과 비용을 나란히 잰다. [recommend.ts:1240](../api/recommend.ts#L1240)에 `_benchModel` A/B 스위치가 이미 있어 하네스는 절반쯤 있다.
- **하나만 고를 필요 없다.** 태깅은 단가·품질, 런타임은 지연·안정성이 기준이다. 다른 제공사를 써도 된다.

### 구조화 출력

양쪽 다 스키마 강제 출력을 지원한다. 어디로 가든 [recommend.ts:726-765](../api/recommend.ts#L726-L765)의 절단 JSON 복구 상태머신을 통째로 지울 수 있다.

## 9. 로그 설계

지금 가중치를 사람이 정하면 "왜 0.15인가"에 답할 수 없다. 나중에 데이터로 튜닝하려면 지금부터 남겨야 한다.

- `recommendation_log.candidates`가 JSONB라 스키마는 준비되어 있다. **항목별 점수 내역**을 같이 넣는다.
- **보여준 것만 로그하면 선택 편향이 생긴다.** 점수는 매겼지만 탈락한 후보도 함께 남긴다.
- 지금 만드는 항목들이 나중에 그대로 학습 피처가 된다. 버려지는 작업이 아니다.

학습 랭커로 넘어갈 시점은 **행동 데이터가 충분히 쌓여서 가중치를 손으로 정하는 것보다 학습시키는 게 나아질 때**다.

## 11. 다음 단계 제안

1. **스코어링 함수를 순수 함수로 분리하고 테스트를 붙인다.** 현재 추천 로직이 825줄 핸들러 안에 갇혀 테스트가 0건이다. 가중치를 손으로 튜닝하려면 회귀 테스트 없이는 매번 감으로 확인하게 된다.
2. 하드 필터부터 구현한다. 정확도 개선의 대부분이 여기서 나온다.
3. 무드 태깅은 키워드리뷰 집계로 1차 버전을 만들고 극단 확인으로 검증한다.
4. 거리 정렬과 샘플링을 붙인다.
5. 커버 지역에서 기존 경로와 A/B 비교한다.
