# 17. 프롬프트 전용 추천 실험 (2026-09-23, dev)

상태: 코드 반영, CLOVA Studio 키 대기. 16번 노트의 방향 2·3·4는 아래 약관 확인으로 폐기됐고, 이 실험이 그 자리를 대신한다.

## 1. 왜

2026-09-07 개정 네이버 검색 API 특약(2.1~2.4)과 카카오 로컬 API 운영정책(데브톡 공식 답변)을 원문으로 확인한 결과, 두 회사 모두 검색 결과를 **LLM에 입력·저장·가공·유료 기능의 근거로 쓰는 것**을 금지한다. 기존 파이프라인(네이버 지역검색 50곳 → Claude 선별 → 재정렬 → recommendation_log 영구 저장 → 야간 블로그 배치)은 이 조항 전부에 걸린다. 구독 BM이면 과금 근거가 지도 API 데이터라는 점이 바로 드러난다.

허용되는 형태만 남기면:
- 모델 기억에서 나온 가게명·좌표는 어느 약관에도 안 걸린다(CLOVA Studio 약관은 결과물로 타 LLM 학습만 금지).
- 카카오 키워드 검색은 **실시간 호출 → 비교 후 버림 → place URL만 보관**이 공식 허용 범위.
- 공공데이터(인허가·상가정보)는 저장·가공 제한 없음.

## 2. 무엇을 바꿨나

| 파일 | 내용 |
|---|---|
| `api/_lib/hcx.ts` | HyperCLOVA X 어댑터. Chat Completions v3, Bearer 키, HCX-007이면 thinking none, jsonSchema 주면 responseFormat json. 테스트 `hcx.test.ts` 7건 |
| `api/_lib/llm.ts` | 벤더 선택. `CLOVA_STUDIO_API_KEY` 있으면 HCX, 없으면 Claude. HCX가 스키마를 4xx로 거부하면 스키마 없이 1회 재시도. 테스트 `llm.test.ts` 4건 |
| `api/_routes/recommend-prompt.ts` | 프롬프트 전용 핸들러. 외부 호출은 카카오 키워드 검색 하나(실존 게이트 + URL). 날씨·혼잡도·공공데이터·네이버·3차 첨부 없음 |
| `api/[...path].ts` | `recommend` 라우트를 새 핸들러로 교체. 기존 `_routes/recommend.ts`는 그대로(export 9개만 추가). 되돌리려면 import 한 줄 |
| `vercel.json` | 야간 크론(`/api/admin/batch`, 블로그 버즈 수집) 제거. 핸들러는 남아 있어 수동 호출은 됨 |

기존 파일을 주석 처리하지 않은 이유: 1,600줄을 주석으로 덮으면 리뷰·복구가 어렵고, 옛 파이프라인이 온전해야 같은 입력으로 A/B가 된다.

## 3. 새 핸들러 흐름

1. 입력 검증·레이트리밋은 기존과 동일(`_lib/guard.ts`).
2. 프롬프트: 지역(행정구역 토큰 또는 중간지점 좌표+반경), 인원·관계·행사·예산·조건 칩·장르·분위기·재추천 제외 목록. "확신하는 영업 중 장소만, 지어내기 금지, 좌표 모르면 0". 단일 10곳(시 전체 12), 2코스 6+6(시 전체 9+9).
3. `askLlm` → `extractPlaces`(기존 부분 복구 파서 재사용).
4. **실존 게이트**: 가게마다 카카오 키워드 검색을 상권 중심 반경(동 2.5km / 구 6km / 시 20km / 스코프 없음 3km)으로 실시간 조회. 이름이 맞으면 통과(정확 일치 → 지점명만 다른 브랜드 일치 순). 통과 시 `kakaoPlaceUrl`만 붙이고 카카오 응답은 버린다. 모델 좌표와 카카오 좌표의 거리는 콘솔 로그에만 남긴다(`modelCoordErrKm`).
5. fitScore 순 정렬, 시 전체면 구 분산·도보 쌍 선택(기존 함수 재사용), 표시 개수 슬라이스.
6. recommendation_log에 모델 출력과 우리 판정만 기록. 카카오 데이터는 URL 외 저장 안 함.
7. 응답에 `_llm: { provider, model, ms, outputTokens, asked, verified }`. `asked` 대비 `verified`가 곧 모델 기억의 실존율.
8. `stage: 'enrich'`는 카카오 URL만 채운다(네이버 이미지검색 제거).

벤더 A/B: 관리자 키(`x-admin-key`)와 함께 본문에 `_provider: 'claude' | 'hcx'`.

## 4. 키 설정

- CLOVA Studio 콘솔 > API 키 > [테스트] 발급 → `.env.local`과 Vercel dev 환경변수에 `CLOVA_STUDIO_API_KEY`.
- 모델 기본 HCX-007. 바꾸려면 `CLOVA_MODEL`(예: HCX-DASH-002. 이 모델은 구조화 출력 미지원이라 스키마 없이 프롬프트 JSON 지시만 탄다).
- 키가 없으면 Claude haiku로 돌아간다(파이프라인 점검용).

## 5. 첫 실측 (Claude haiku, 키 없는 상태)

강남역·역삼역 중간, 밥, 4명, 2~4만원, 아늑한+조용하게 → 10곳 생성, **실존 0곳**("강남역 우육면", "역삼 소문난 된장찌개" 같은 지어낸 이름). 게이트가 전부 걸러 500("확인된 장소 없음"). haiku는 국내 가게 지식이 없다는 기준선이고, HCX 기본 가설의 비교 대상.

## 6. 측정 방법

같은 입력 30건을 `_provider`로 두 벤더에 보내고 기록:
- 실존율: 응답의 `verified / asked`
- 좌표 오차: Vercel 로그의 `modelCoordErrKm` 분포(중앙값, 1km 초과 비율)
- 지점 오류: 로그의 `match=brand` 비율
- 조건 적합: 사람이 카카오 place URL로 확인(분위기·가격대·업종)

## 7. 이 다음

- 좌표는 모델 대신 공공데이터(인허가·상가정보)로 채운다. 이름·주소 매칭 → 좌표·영업상태. 인허가 배치는 현재 영업(01)만 적재하므로 폐업(03)도 담아야 확정 탈락이 된다.
- 실존율이 쓸 만하면 후보 채널로 확정하고, 기존 recommend.ts와 blogBuzz.ts·publicData L0·purposeGate는 삭제. place_buzz_cache는 DB 개편 SQL에서 drop.
- 프로덕션(main)의 기존 파이프라인은 릴리즈 전까지 그대로. 최소 조치가 필요하면 recommendation_log 21일 삭제와 3차(카카오) 저장 제거.

- 요금(ncloud 요금 API, 2026-09-23): HCX-007·HCX-005 입력 0.00125원/토큰, 출력 0.005원/토큰. 1회 추천 = 단일 코스 약 8원(입력 ~900, 출력 ~1,400 토큰), 2코스 약 11원(호출 2회). 카카오 키워드 검색은 무료 쿼터 안.

## 9. 1차·2차 거리 처리 (2026-09-24 정리)

**결론: LLM은 거리를 판단하지 않는다. 거리는 코드가 계산한다. 이전 모델 대비 사실상 달라진 것은 없다.**

- 현재 모델은 LLM에 거리 정보를 넣지 않는다(적용 예정, 현재 프롬프트에는 "중심에서 N m"이 남아 있음). 이 거리는 카카오 검색 응답에서 나온 값이고, 카카오는 API 응답 데이터를 외부 LLM에 전송하는 것을 허용하지 않는다(데브톡 공식 답변, 2026-09-08. 질문 항목에 "거리"가 명시돼 있었음).
- 거리 반영은 코드가 한다. 중심에서 1km당 4점 감점. LLM이 거리를 보지 않아도 순위 품질은 떨어지지 않는다. 오히려 지금은 모델과 코드가 거리를 이중으로 반영하고 있다.
- 이전 모델(네이버 지역검색 + Claude haiku)도 1차·2차 도보 연결은 제대로 동작하지 않았다.
  - 프롬프트에 좌표를 넣고 "1순위끼리 도보 15분 이내 조합 우선"이라고 지시했을 뿐이다. LLM은 좌표로 거리를 계산하지 않는다. 숫자나 동 이름으로 짐작하는 수준이다.
  - 그 뒤 코드가 1차·2차를 각각 따로 재정렬해 1위끼리 붙였다. 거리 기준 쌍 선택은 시 전체 추천일 때만 켜져 있었다.
  - 1차·2차가 대체로 가까웠던 건 네이버 검색이 상권 이름으로 검색해 후보가 한 상권에 몰렸기 때문이지, 거리 계산 덕이 아니다.
- 현재 모델도 같은 구멍이 있다. 1차·2차를 병렬로 따로 받아 각각 샘플링하고, 쌍 선택은 시 전체에서만 동작한다. 후보를 중심 반경 전체에서 모으므로 1차·2차가 반경 양 끝(최대 4~5km)으로 갈릴 수 있다.
- 대응(예정): 모든 스코프에서 코드로 쌍을 고른다. 1차를 뽑은 뒤 2차 점수에서 1차까지 도보 1분당 감점해 샘플링. LLM 호출·카카오 데이터 전송은 늘지 않는다.

## 10. 결정 대기 (2026-09-24)

1. **클라이언트 저장 정리.** 결과 스냅샷(localStorage, 24시간)과 히스토리(무기한)에 카카오 상호·좌표·주소가 남는다. 카카오는 기기 저장도 place ID·URL만 허용한다. 안: place id·URL·우리 점수만 저장하고, 화면을 다시 그릴 때 id로 카카오를 재조회해 표시. 순위 품질에는 영향 없음.
2. **가격대·적합도 점수 표시.** 검색 우선 구조와 무관하게 여전히 모델 추측이다. 안: "추정" 표기 또는 화면에서 제거. 기획 결정 필요.

### 10-1. 카카오 저장 규정 추가 조사 (2026-09-24)

- **근거 조항**: Kakao Developers 운영정책(2026-04-20 시행) 제5조 금지행위 중 "앱에서 사용자 환경을 개선하기 위한 목적 외 다른 목적으로 카카오에서 받은 데이터를 캐시하거나 캐시 후 최신 데이터로 유지하지 않는 행위". 문언상 **사용자 환경 개선 목적의 캐시는 허용**되고, 최신 상태 유지가 조건.
- **카카오 실무 해석은 훨씬 좁다**(데브톡 공식 답변):
  - 장소 ID·place_url만 저장 가능. 장소명·주소·좌표·전화·카테고리는 저장 불가(05-08, 08-21, 09-01, 09-17).
  - 사용자가 직접 고른 장소의 이름도 DB 저장 불가, "제5조 20호의 캐시 목적에 해당하지 않음"(09-17). 08-21 답변은 사용자 선택 장소명 저장을 허용했으나 09-17 답변이 더 최신이고 엄격.
  - 임시 저장도 불가: 세션당 20분(08-24), 서버 1시간 캐시(07-23).
  - 응답 기반 **2차 가공물 저장 불가**: API 결과로 만든 범주형 평가값 저장 불허(09-21).
  - **ID로 단건 조회하는 API는 없다**. 저장한 ID로 이름·좌표를 되살리려면 재검색뿐(08-21 답변에서 카카오도 인정).
- **우리 코드에 새로 걸리는 것**:
  - recommendation_log의 fitScore·known·finalScore: 카카오 결과를 입력으로 만든 값이라 "2차 가공물"로 볼 여지가 있다.
  - place_category 테이블: 카카오 category_name을 모은 것. "카테고리 정보의 저장 활용은 불가"(08-21) 답변과 정면으로 충돌.
  - 클라이언트 결과 스냅샷(localStorage 24시간)·히스토리: 브라우저 저장에 대한 직접 답변은 없음. 조문상 "사용자 환경 개선 목적 캐시"로 주장할 여지는 있으나, 20분 임시 저장도 불허한 선례가 있다.
- **재검색 비용 정정**: 복원 시 재검색은 카카오 검색만이고 LLM은 다시 부르지 않는다(순위·설명은 우리 값). 다만 1·2차 합쳐 카카오 호출 수십 회라 느리다.
- **다음**: 데브톡에 우리 사례로 직접 문의(아래 초안). 답변 전까지 결정 보류.

2. (보류 — 점수 표시 제거 결정 시 불필요) 자체 점수 저장: 장소 ID와 함께 우리 서비스가 사용자 조건(인원·예산·분위기)으로 매긴 적합도 점수와 노출 순위를 저장하는 것이 "2차 가공물"에 해당하는지. 점수 산정에는 카테고리·거리 등 응답값이 입력으로 쓰입니다.
3. (보류 — 내부 판단) 카테고리 분류표: 개별 장소와 무관하게 category_name 문자열의 종류("음식점 > 한식 > 국밥" 등)만 모아 사용자 선택 필터 목록으로 쓰는 것이 허용되는지. 장소명·ID·좌표는 함께 저장하지 않습니다.

### 10-2. 결정 (2026-09-24, 유저)

- **카카오 문의는 하지 않는다.** 브라우저 보관은 선례(20분 임시 저장 불허, "live call only")로 이미 막힌 것으로 본다.
- **저장은 장소 ID·place_url만.** 서버·클라이언트 모두. 장소명·주소·좌표·카테고리·모델 설명은 어디에도 남기지 않는다.
- **추천 기록은 장소 ID로 슬롯을 표현한다.** 1차·2차·대안 각 슬롯에 어떤 장소 ID를 보여줬는지 + 사용자가 누른 장소 ID. 적합도·known·최종 점수는 저장하지 않는다(화면에서도 점수 제거 방향, 기획 합의 대기).
- **지난 추천(회원 50건·90일)**: 날짜·지역·목적·인원(사용자 입력) + 슬롯별 place_url. 화면은 "카카오맵에서 보기" 링크.
- 남은 결정: 새로고침 시 결과가 사라지는 것을 어떻게 처리할지(10-3 참고).

### 10-3. 저장 정리 작업 계획 (2026-09-24, 미착수)

**핵심 장치: 복원 요청.** 검색 조건 + 슬롯별 장소 ID를 받으면 서버가 추천 때와 같은 카카오 검색을 다시 돌려 ID가 일치하는 가게의 이름·주소·좌표·링크를 돌려준다. LLM 호출 없음. 못 찾은 슬롯은 place URL 링크만. 추천 응답에 검색 조건(중심 좌표, 반경, 목적·장르, 키워드, 행정구역, 완화 단계)을 실어 클라이언트가 보관.

근거: 카카오는 ID·URL 저장만 허용하고 ID 단건 조회 API가 없어 "재조회는 새 검색"(데브톡 08-21). 카카오 검색은 같은 조건이면 같은 결과이고, 달라지는 건 가게 신규·폐업·정보 수정·카카오 색인 갱신 때뿐.

**1단계(이번 작업)**
1. 결과 스냅샷: 폰에는 검색 조건·슬롯별 ID·URL·사용자 입력만. 새로고침 시 복원 요청. 모델 설명·태그·가격대는 복원 안 됨.
2. 로컬 히스토리(랜딩 "지난 추천"): 비회원 이력 없음 정책에 따라 제거. 회원 서버 목록은 DB 개편 때 같은 방식.
3. 공유 링크: mint_share_snapshots에 가게 정보 전체 저장 중 → 조건·ID만 저장, 링크 연 화면에서 복원.
4. 그룹 결과: mint_sessions.result_json에 가게 정보 전체 저장 중 → 조건·ID만, 게스트 화면에서 복원.
5. 추천 기록·분석 이벤트: recommendation_log는 슬롯별 ID·클릭 ID만(점수 제거). 클릭·거절 이벤트의 placeName·address → 장소 ID.
6. 파일럿 핸드오프(폰에 가게명 저장): 파일럿 운영 여부 확인 후 변경 또는 제거.

**2단계(회원 DB 개편 때)**
- 찜: 폰에 이름·주소·좌표 저장 중 → 회원 서버 기능으로 옮길 때 ID·URL·검색 조건으로 저장, 목록 열 때 복원.
- 방문 인증: 중복 판정을 이름+주소 → 장소 ID로. GPS 300m 판정용 좌표는 인증 순간 복원 요청으로 받아 비교 후 폐기. "예약하러 가기 누른 가게만" 조건도 이때.

**사용자 경험 변화**: 새로고침·공유 링크·게스트 화면에 1~3초 복원 로딩. 그 화면에선 모델 설명·태그 없음. 오래된 링크는 일부 가게가 링크로만 보일 수 있음.

### 13. [1-1 BE] 회원 데이터 서버 저장 — 논의 결과와 할 일 (2026-09-29)

**기획자 합의 대기**
- 쌓이는 기능(찜·포인트·방문 인증·지난 추천·16번 자동 채우기)은 회원 전용. 비회원은 추천받기·공유·그 회차 임시 저장만. 유저 입장: 비회원 데이터는 localStorage·DB 어디에도 남기고 싶지 않음.
