상태: 회의 결과 + 그날 저녁 논의 정리. **코드·스키마 변경 없음.** 내일 이어서 결정할 것은 4절.

## 1. 회의 결과 (확정, 2026-09-29)

- 데이터를 쌓는 기능은 회원 기능: 찜, 포인트, 방문 인증, 지난 추천, 지난 조건 자동 채우기(16번)
- 일회성 기능은 비회원 기능: 추천받기, 다시 추천받기, 결과 공유, 모임 링크 참여
- 비회원 데이터는 저장하지 않는다. localStorage의 문제(삭제·시크릿·iOS 7일·인앱 분리·조작 가능)를 기획자에게 전달함
- 회의에서 못 다룬 것: 지난 추천 보관량

## 3. 저장 분류 (제안 — 유저 의견 반영, 미확정)

"비회원 데이터를 저장하지 않는다"를 글자 그대로 적용하면 공유·그룹·새로고침 복원이 성립하지 않는다. 유저 제안: 기능을 위한 **임시 보관**은 저장이 아니라 보관으로 본다. 아래는 그 기준으로 나눈 것.

| 분류 | 무엇 | 식별자 | 보관 | 비고 |
|---|---|---|---|---|
| 회원 데이터 | 찜, 포인트 내역, 방문 인증, 지난 추천 | user_id | 지난 추천 90일·20건(미확정), 나머지는 탈퇴 시까지 | 1-1 범위 |
| 임시 보관 | 추천 결과(검색 조건 + 슬롯별 장소 ID), 공유 링크, 그룹 모임 | 기록마다 임의 ID. **기기 ID 아님** | 본인 복원 6시간 / 공유·그룹 7일(제안) | 만료 삭제 작업 필수 |
| 식별자 없는 이용 통계 | 조건, 지역(상권·행정구역 수준), 슬롯 장소 ID, 슬롯 행동 | 없음 | 계속 | 임시 보관 행이 만료되면 출발지를 지우고 통계 행으로 남김 |
| 운영 로그 | api_hits(레이트리밋), client_errors | IP / 없음 | api_hits 1일, client_errors 30일(제안) | 삭제 작업 필요 |
| 기기에만 | 입력 초안(추천 받기 전 선택값), 임시 보관 기록의 ID | - | 6시간, 새 추천 시 삭제 | 18번 A-4(입력 조건 유지)와 일치 |

판단 근거:
- **기기 ID를 안 쓰는 이유**: 기록 단위 임의 ID면 같은 기기의 기록끼리 이어지지 않는다. 기기 ID는 이어 버려서 "비회원을 식별하지 않는다"와 어긋난다.
- **공유 6시간이 짧은 이유**: 모임은 보통 며칠 뒤. 친구가 다음 날 열면 만료. 저장 내용이 조건과 장소 ID뿐이라 기간을 늘려도 부담 없음.
- **통계에서 출발지를 지우는 이유**: 출발지 검색어·장소 ID는 집 근처 역일 수 있는 준식별 정보.
- **찜 없이도 비회원 통계가 의미 있는 이유**: 카카오맵 열기(관심), 예약하러 가기(강한 의사), 공유, 다시 추천받기와 사유(거절), 공유 투표가 남는다.
- **식별자 없어서 잃는 것**: 같은 사람의 재사용 추적, 한 사람 중복 클릭 제거, 방문 인증 연결. 앞 둘은 감수, 방문은 회원 데이터에서.

테이블별 유저 평가(09-29): api_hits·events는 쓸모없는 데이터, client_errors는 조금 쓸모 있음.
- api_hits는 분석용이 아니라 레이트리밋 장치라 없애면 LLM 비용 상한이 사라진다. 하루 지난 행 삭제로 충분.
- events는 정리 대상. 40종 넘는 이벤트가 JSON payload, 절반이 목업 기능. 어드민 대시보드와 /api/count가 읽고 있어 어드민 교체 후 제거. 비회원 퍼널은 GTM으로.
- client_errors는 유지. 18번 노트 36번(카카오 복귀 토큰이 URL째 저장)은 수정 필요.

미확인: 만료된 그룹 세션·공유 스냅샷을 지우는 작업이 지금 있는지, api_hits 삭제 작업이 있는지. 코드 확인 필요.

## 4. 열린 결정 (순서대로)

1. **LLM 입력 문제.** 17번 노트 1·9절은 카카오가 API 응답의 외부 LLM 전송을 금지한다고 적고 거리를 프롬프트에서 뺐다. 그런데 현재 dev 프롬프트의 후보 목록은 `번호 | 상호 | 업종 | 동네`이고 셋 다 카카오 응답이다. 검색 우선 구조 자체가 걸린다. 선택지:
   - (가) LLM 없이 코드만으로 순위: 카테고리 필터 + 거리 + 도보 쌍 + 시드 샘플링. 09-23 재현에서 HCX의 known이 75곳 중 0~7곳이라 지금도 LLM 기여가 작다. 설명·태그는 없어짐
   - (나) 모델 기억 후보 + 카카오 실존 확인으로 복귀(17번 원래 실험). 약관에 맞지만 같은 가게 반복·후보 전멸이 돌아옴
   - (다) 후보 소스를 공공데이터(상가정보·인허가)로. LLM 입력·저장 제한 없음. 카카오는 URL 확인만
   - 이게 정해져야 슬롯·복원 설계가 확정된다(17번 11절 "검색 방식이 먼저")
   - **확정(2026-09-30, 유저): 09-24 결정 유지.** 검색 우선 구조(카카오 후보 → 코드 필터 → HCX 순위)를 그대로 간다. 빼면 장소 추천 자체가 무너진다. 약관 충돌은 감수하고, 노출 최소화 쪽으로만 다룬다. 슬롯·복원 설계는 이 구조 기준으로 확정.
2. **임시 보관 기간.** 본인 복원 6시간 / 공유·그룹 7일 제안. 유저 원안은 전부 6시간.
3. **비회원 통계 수집 여부.** 유저가 제안, 3절 구조로 가능. 기획자에게 "비회원 데이터 저장 안 함"과의 관계를 설명해야 함.
4. **폰 데이터 옮김(3번).** 기존 폰의 찜은 네이버 파이프라인 시절의 이름·주소라 카카오 장소 ID가 없다. 새 구조는 ID만 저장하므로 그대로 못 옮김. 제안: 옮기지 않고 공지. 운영 사용자가 적은 지금이 가장 쌈.
   - **확정(2026-09-30, 3번): 비회원 통계 수집한다.** 식별자 없이 단순 집계와 추후 알고리즘 반영용 데이터로만.
   - **확정(2026-09-30, 5번): 지난 추천 보관 상한 20건**(90일과 함께, 설정값).
   - **확정(2026-09-30, 2번): 본인 복원은 localStorage**(검색 조건 + 슬롯별 장소 ID, 휘발 감수). **공유는 공유하기 버튼을 누를 때만 서버에 올리고 7일 뒤 배치로 삭제**(삭제 작업 신규 필요). 그룹 모임도 서버 7일(제안).
   - **확정(2026-09-30, 4번): 폰 데이터는 옮기지 않는다.** 운영 이관 때 DB 초기화(백업 먼저), 새 버전 코드가 처음 실행될 때 옛 localStorage 키(찜·포인트·인증·이력 등) 삭제.
   - **확정(2026-09-30): 사용자 상태는 Zustand store 하나로.** 회원 상태 조회가 여러 화면·서비스 코드에서 필요하고, 추후 구독 서비스까지 대비. store는 로그인 구독 1회 + 세션·회원 여부·로딩·닉네임·사진(구독 등급 자리 확보). 찜·포인트 같은 서버 데이터는 store에 넣지 않고 기능별 hook. 구독 등급은 화면 표시용일 뿐, 권한 판정은 반드시 서버(RLS·API)에서. 익명 로그인 제거와 함께, 1-1 스키마 다음·회원 화면 전에 작업.
5. **지난 추천 보관량.** 회의 미논의. 17번 13절은 90일·20건·화면 10건, 18번 A-3은 50건·90일을 "확정"으로 적음. 설정값이라 20건으로 넣고 사후 확인 제안.
6. **포인트 유효기간.** 회의에서 다뤘는지 미확인.
7. **가격대·적합도 점수 표시.** 회의에서 다뤘는지 미확인. 1번이 (가)로 가면 자동으로 사라짐.
8. **기획자 재전달.** 임시 보관과 비회원 통계를 예외로 둔다는 것, 데이터 수집이 회원 위주가 되어 로그인 전환율이 핵심 지표가 된다는 것. 개인정보처리방침 반영.
