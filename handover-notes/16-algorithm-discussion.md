# 16. 알고리즘 논의 정리 (2026-09-21~23)

상태: 논의 결과 정리. 07번 노트(옛 설계, 크롤 DB 전제)는 무효. **2026-09-23 추가: 네이버 검색 API 특약(09-07 개정)과 카카오 로컬 정책이 검색 결과의 LLM 입력·저장을 금지하는 것을 확인. 5절의 방향 2·3·4와 3절의 "데이터 출처 검토 종료"는 폐기. 현재 기준은 17번 노트.**

## 1. 현재 알고리즘 (코드 실측, api/_routes/recommend.ts)

1. 출발지 → 중간지점(클라이언트, 직선 중간점 + 대중교통 실측으로 상권 결정)
2. 네이버 지역검색: 목적별 키워드 10개 × display 5 → 최대 50곳. 키워드는 코드 상수 4개(목적·장르·특별한 날·관계). `sort=random`
3. 거리·행정단위·편식 필터. 편식은 이름·카테고리 문자열만, 0곳 되면 필터 포기
4. 공공데이터 발굴 후보 주입(L0): 반경 내 상가 전수 → 네이버에 없는 것 → 업종 정규식(밥/술/카페) → 업력 상위 3곳
5. Claude haiku가 후보 목록(이름|카테고리|주소|좌표)만 보고 파이널리스트 최대 12곳 선별 + 적합도 0~100 + 설명·가격대·태그 작성. **도구·검색 없음**
6. 번호(sourceIndex)로 네이버 원본을 덮어써 실존 보장. 설명·가격대·태그·점수는 모델 출력 그대로 (검증 없음)
7. 버즈 감점(L1, 야간 배치가 인기상권 18곳만 캐시) + 순위 보정(L3: 노출-적합도 괴리, 발굴 가산, 키워드 가산)
8. 최종 점수로 1차·2차 대표 + 대안 슬라이스(3곳 또는 6곳). 시 전체면 구 분산
9. 3차 자동 첨부(카카오 로컬 카테고리, 마지막 코스 1.5km)
10. recommendation_log 기록, enrich(사진·URL) 별도 호출

## 2. 사용자 조건이 실제로 반영되는가

| 등급 | 조건 |
|---|---|
| 보장됨(서버가 좌표·주소·업종으로 직접 거름) | 지역, 거리, 목적 대분류, 재추천 제외(3곳 미만이면 안 함) |
| 검색어에 단어만(결과 검증 없음) | 장르, 5명 이상("단체"), 예산 양극단("가성비"/"고급"), 특별한 날 5종, 관계 2종(연인·가족), 편의시설 칩 3개 |
| 문자열 필터 | 못 먹는 음식(이름·카테고리만, 0곳이면 포기) |
| 프롬프트 문장만(모델이 이름 보고 추측) | 분위기 전부, 예산 중간, 4명 이하, 관계 "친구들", 날씨·시간 |
| 아무 효과 없음 | "오랜만에"·"그냥 한잔"·"평범한 데이트"·"명절"·"그냥 식사" 칩(서버로 null) |
| 화면에 나가지만 검증 안 된 값 | 가격대, 분위기 태그, 한 줄 설명, 적합도 점수 |

빈 분위기는 "활기찬 분위기"로 뒤집혀 들어간다(`isQuiet` 이분법, recommend.ts ~1130). 삼분법으로 고쳐야 함.
선택지 정의가 3파일에 흩어짐(HomeStepsView REL_OPTIONS, constants/occasion.ts, recommend.ts 사전 2개). 한 곳으로 모아야 함.

## 3. 결정된 것

- **"못 먹는 음식" 입력 항목 제거** (2026-09-21 유저). 알레르기 리스크 — 어떤 데이터로도 보장 불가, 고정 칩으로 바꿔도 유저가 알레르기 필터로 오해. 결정 로그 초안은 유저가 보유
- **비회원은 찜·포인트·인증·이력 없음** (14번 노트). 회원=`is_anonymous=false`
- **출시 버전의 약속 범위**: 데이터 없이 보장되는 것만 — 위치·거리·업종·장르·폐업·업력·인증·혼잡도·날씨·동선. 못 지키는 조건은 입력에서 빼거나 "취향 메모"로 격하. 적합도 점수·추정 가격대는 화면에서 제거 또는 "추정" 표기(기획 결정)
- **데이터 출처 검토 종료**: Google Places 불가(non-Google 지도와 병용 금지 약관, 30일 캐시 제한), TourAPI 관광지 위주라 무의미, 블로그 API는 근거용(필터 아님, 없으면 침묵), 네이버 플레이스 "MCP"는 전부 스크레이퍼(크롤링=팀 정책 위반). 합법 소스는 위치·업종·업력·폐업·인증·혼잡도·날씨 + 유저 선택 데이터 + 사장님 입력뿐

## 4. 경쟁 상황

네이버 **플레이스 에이전트** 2026-09-17 네이버지도 앱 출시: 대화로 조건(인원·주차·시간·음식) 받아 방문자 리뷰·블로그·예약 반영 추천 + 예약 연결. 외부 API 없음. "조건 맞는 맛집 찾기"는 네이버가 이김. MINT가 할 수 있고 네이버가 안 하는 것: **여러 출발지 중간지점, 링크 하나로 그룹 취향 취합, 1·2·3차 코스 동선**. 이 셋이 정체성.

## 5. 다음 알고리즘 방향 (합의)

원칙: "데이터로 계산 가능한 건 코드가 점수, LLM은 탐색·근거·설명". 이미 쓰는 API를 더 똑똑하게 묻는다.

| 순서 | 방안 | 효과 | 비용 |
|---|---|---|---|
| 1 | **검색어에 조건 반영** + `sort=comment` 병행. 분위기·관계·특별한 날 단어를 지역검색 쿼리에 넣는다(네이버 엔진이 리뷰·키워드로 정렬해 줌 — 리뷰를 안 줘도 리뷰로 정렬된 결과는 준다) | 가장 큼. 지금 분위기는 검색어에 0 반영 | 반나절. comment 정렬은 거품 편향이라 random과 섞기 |
| 2 | **파이널리스트 블로그 발췌 주입**: "가게명 + 조건 단어"로 블로그검색 → 발췌 200자를 모델에 근거로. 12곳 병렬 1초, 쿼터 2.5만/일 여유 | 유명 가게에서 추측→근거. 동네 가게는 여전히 없음 | 하루 |
| 3 | **모델 기억으로 후보 생성 채널**: "홍대 분위기 좋은 술집으로 유명한 곳 5개" → 지역검색으로 실존·좌표 확인(지어낸 건 탈락). 키워드 검색 옆 두 번째 채널 | 기억을 검증 가능한 자리(실존)에만 씀 | 하루 |
| 4 | **에이전트 루프**: 위 셋을 손코딩 대신 LLM function calling으로. 우리 서버가 지역검색·블로그검색을 함수로 정의, 모델이 부르면 서버가 대신 호출. 도구 호출 예산 상한(예: 지역 5 + 블로그 12), 구조화 JSON 출력 필수 | 사전 4개 유지보수 소멸 | 지연 10~20초·토큰 4~8배. 예산 상한이 핵심 |

**코드가 반드시 쥐는 것**(모델에게 안 넘김): 지역·반경·중간지점·그룹 취합·코스 동선 / 폐업·업종·재추천 제외 / 도구 호출 상한 / 구조화 출력·기록.

## 6. LLM 벤더

- 유저 입장: HyperCLOVA X가 네이버 데이터를 압도적으로 더 학습했으니 국내 가게 지식이 낫다. 타당.
- HCX가 유리한 자리: 기억 기반 후보 생성(5-3), 이름 보고 속성 판단. 벤더 무관한 자리: 검색어 생성, 도구 호출, 발췌 읽고 판단.
- **계획**: `api/_lib/claude.ts` → `llm.ts`로 이름 바꾸고 어댑터 2개(Claude, HCX). CLOVA Studio 키(유저 발급) 받으면 HCX 붙임. 실험은 "모델 교체"가 아니라 "에이전트 루프 구조" 기준으로, 실제 추천 30건 × 후보 60곳을 사람이 네이버 플레이스에서 정답표 만들어 가격대·분위기·폐업 오답률 비교. HCX를 기본 가설로.
- 어느 모델이든 기억은 검증 없이 화면에 못 나감: 지역검색 실존 확인 + 블로그 근거 필수.
